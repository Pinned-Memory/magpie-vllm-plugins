Where the memory went

The checkpoint is 171 GB on disk. Everything but the n-gram table is resident; the table is read through the page cache, 16 rows of 320 bytes per token.

How it works

  • No copy, no new I/O path. vLLM's default safetensors loader already opens the checkpoint with mmap and hands each of the 128 n-gram shards over as a zero-copy CPU view. Patch 0001 keeps those views instead of copying them into a 102 GB device parameter, and calls madvise(MADV_RANDOM) on each so a miss reads one 4 KiB page instead of the kernel's 128 KiB readahead.
  • Gather. Hash the n-gram ids on the GPU (stock code), torch.unique, one copy of the unique ids to the host, sorted ids split by shard run across 16 threads (page faults overlap on the NVMe), rows land in a pinned buffer, one async copy back up, inverse index expands on the GPU.
  • Full CUDA graphs (patch 0002). The runner's model-state input prep, called immediately before the forward, stages the step's rows into a static device buffer; the forward only reads a slice of it. That removes the custom op, the graph-splitting entry and the PIECEWISE forcing, so target decode and the MTP draft's decode steps replay full graphs.
  • MTP pruning (mtp-pruning patch). draft_vocab_path in --speculative-config gives the Qwen4Exp drafter a 10,010-row slice of the target head (49 MB instead of 1.2 GB) and scatters its logits back to full-vocab positions. The keep-set was fitted on this model's own generations (87k tokens) and unioned with the Qwen3.8-27B agent set; the tokenizers are identical.
  • Activation is a vLLM argument on the HF config namespace, next to the PLE layout attributes the layer already reads: --hf-overrides '{"ple_mmap": true}'. Unset, every patched file behaves stock.

Run it

# vLLM checkout at 33898f832c (v0.29.0rc1); patches apply alone or stacked
git -C /path/to/vllm apply patches/ple-ssd/0001-qwen4-exp-ple-table-on-ssd.patch
git -C /path/to/vllm apply patches/ple-ssd/0002-stage-rows-before-forward-full-cudagraphs.patch
git -C /path/to/vllm apply patches/mtp-pruning/0001-mtp-draft-vocab-pruning.patch

# serve (memory-conservative GB10 defaults; MTP=0 disables speculation)
DRAFT_VOCAB_PATH=$PWD/scripts/flash_next/results/keep_flashnext_p99.pt \
GPU_MEM=0.76 MAX_NUM_SEQS=4 scripts/flash_next/serve.sh server.log --language-model-only

# measure
python scripts/flash_next/bench_decode.py --concurrency 1 --num-prompts 8 --out bench_c1.json
python scripts/flash_next/gsm8k_eval.py -n 200 --out gsm8k.json
scripts/flash_next/profile_decode.sh && scripts/flash_next/trace_summary.py results/<run>/trace/*.gz

First launch JIT-builds FlashInfer's sm_120 fused-MoE kernel (about 5 minutes, needs ninja and nvcc on PATH; the serve script exports both). Weight loading takes about 10 minutes per launch.

Limits and next levers

  • BF16 and FP16 tables only; the official FP8 checkpoint's global table scale is not carried through the mmap path yet.
  • The keep-set is fitted on a small corpus (87k tokens); acceptance dropped 4–7 % versus the full head where the 27B saw 1 %. Recount on real agent traffic before shipping it.
  • Cold rows cost an NVMe read; a first pass over new text is slower than the second. An FP8 copy of the table on disk would double the page-cache hit rate for the same memory.
  • The profile says the next real lever is the checkpoint's BF16 side layers (58 % of a pruned step): converting them to blockwise FP8, as the reference recipe's "hybrid" mode does, is the obvious follow-up.
  • Per-launch weight loading is about 10 minutes at 150–200 MB/s; it is CPU-bound in the NVFP4 expert loader, not disk-bound.
